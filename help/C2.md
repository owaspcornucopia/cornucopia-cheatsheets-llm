# C2 — Dangerous Programming Patterns

## Threat

An attacker can bypass application controls because dangerous programming language functions have been used instead of safer alternatives.

## How This Applies

The application uses several dangerous programming patterns:

- **Direct database execution with unsanitized input** — [all three implementations](#implementations) execute an untrusted SQL string, a dangerous pattern that should be replaced with parameterized queries
- **Permissive fallback parsing** — when JSON parsing fails, the [Python implementation](https://github.com/owaspcornucopia/llm-companion-scenario) accepts Python literal syntax, the [.NET implementation](https://github.com/owaspcornucopia/llm-companion-scenario-dotnet) normalizes malformed JSON or accepts raw SQL, and the [TypeScript implementation](https://github.com/owaspcornucopia/llm-companion-scenario-typescript) accepts raw SQL output directly
- **JSON parsing of LLM output** — processes untrusted model output without size limits or schema validation
- **String formatting in SQL inserts** — [all three implementations](#implementations) construct seed-data SQL with string interpolation instead of parameter binding

The most critical dangerous pattern is the direct execution of LLM-generated SQL. This is fundamentally equivalent to using `eval()` on user input — the application takes untrusted strings and executes them as code (SQL code, in this case).

## Example Attack

An attacker crafts LLM output that strict JSON parsing rejects but a fallback path accepts. The [Python implementation](https://github.com/owaspcornucopia/llm-companion-scenario) can accept Python literal syntax, the [.NET implementation](https://github.com/owaspcornucopia/llm-companion-scenario-dotnet) can recover malformed tool calls or treat remaining output as SQL, and the [TypeScript implementation](https://github.com/owaspcornucopia/llm-companion-scenario-typescript) accepts raw SQL. In [any of the three implementations](#implementations), a permissive parser turns malformed model output into executable database input.

## Mitigations

1. **Replace direct SQL execution with parameterized queries** — never pass untrusted strings directly to the database engine.
2. **Remove permissive fallback parsing** — enforce strict JSON-only output from the LLM and reject anything that does not match the expected schema.
3. **Use parameterized SQL for seed data and runtime queries** — replace string interpolation with proper parameter binding.
4. **Add schema validation** on parsed JSON before using it — verify the structure matches expectations using a schema validator.
5. **Use the safest available function** for each operation — prefer parameterized queries, strict JSON parsing, and typed data handling.
