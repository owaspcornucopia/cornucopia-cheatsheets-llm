# C2 — Dangerous Programming Patterns

## Implementations

- [Python implementation](#python-implementation)
- [.NET implementation](#net-implementation)
- [TypeScript implementation](#typescript-implementation)
- [Java implementation](#java-implementation)

## Threat

An attacker can bypass application controls because dangerous programming language functions have been used instead of safer alternatives.

## How This Applies

### All implementations

The application uses several dangerous programming patterns:

- **Direct database execution with unsanitized input** — all four implementations execute an untrusted SQL string, a dangerous pattern that should be replaced with parameterized queries
- **Permissive fallback parsing** — when JSON parsing fails, each implementation handles it differently
- **JSON parsing of LLM output** — processes untrusted model output without size limits or schema validation
- **String formatting in SQL inserts** — all four implementations construct seed-data SQL with string interpolation instead of parameter binding

The most critical dangerous pattern is the direct execution of LLM-generated SQL. This is fundamentally equivalent to using `eval()` on user input — the application takes untrusted strings and executes them as code (SQL code, in this case).

### Python implementation

When JSON parsing fails, the Python implementation accepts Python literal syntax.

### .NET implementation

When JSON parsing fails, the .NET implementation normalizes malformed JSON or accepts raw SQL.

### TypeScript implementation

When JSON parsing fails, the TypeScript implementation accepts raw SQL output directly.

### Java implementation

When JSON parsing fails, the Java implementation accepts raw SQL output directly.

## Example Attack

### All implementations

An attacker crafts LLM output that strict JSON parsing rejects but a fallback path accepts. In any of the four implementations, a permissive parser turns malformed model output into executable database input.

### Python implementation

The Python implementation can accept Python literal syntax.

### .NET implementation

The .NET implementation can recover malformed tool calls or treat remaining output as SQL.

### TypeScript implementation

The TypeScript implementation accepts raw SQL.

### Java implementation

The Java implementation accepts raw SQL.

## Mitigations

1. **Replace direct SQL execution with parameterized queries** — never pass untrusted strings directly to the database engine.
2. **Remove permissive fallback parsing** — enforce strict JSON-only output from the LLM and reject anything that does not match the expected schema.
3. **Use parameterized SQL for seed data and runtime queries** — replace string interpolation with proper parameter binding.
4. **Add schema validation** on parsed JSON before using it — verify the structure matches expectations using a schema validator.
5. **Use the safest available function** for each operation — prefer parameterized queries, strict JSON parsing, and typed data handling.
